## 개요

팀에서 릴리스마다 변경 로그를 손으로 정리하고 있었습니다. 커밋 메시지 컨벤션은 이미 지키고 있었는데도, 그걸 다시 읽어서 문장으로 옮기는 작업이 매번 반복됐습니다.

gitlog는 두 태그 사이의 커밋을 읽어 타입별로 묶고, 이슈·PR 링크를 붙이고, breaking change를 맨 위로 올려 Markdown을 출력합니다. 기계적인 부분만 자동화하고 요약 문장은 사람이 쓰도록 남겨둔 게 설계 의도입니다.

## 주요 기능

- **커밋 파싱** — `feat(scope)!: ...` 형태를 파싱해 타입·스코프·breaking 여부를 뽑아냅니다. 컨벤션을 어긴 커밋은 버리지 않고 "기타" 섹션으로 모아 보여줍니다.
- **범위 자동 추론** — 인자가 없으면 가장 최근 태그부터 HEAD까지를 기본 범위로 잡습니다.
- **템플릿 커스터마이즈** — 섹션 순서와 제목을 설정 파일로 바꿀 수 있습니다. 한국어 섹션명이 첫 요구사항이었습니다.
- **GitHub Actions 통합** — 태그 푸시 시 릴리스 본문을 자동으로 채우는 워크플로 예제를 함께 제공합니다.
- **드라이런** — `--dry-run`으로 파일을 건드리지 않고 결과만 확인합니다. 파괴적 동작은 전부 옵트인입니다.

## 배운 것

CLI의 UX는 에러 메시지에서 결정됩니다. 초기 버전은 태그가 없을 때 스택 트레이스를 그대로 뱉었고, 그게 유일한 사용 후 불만이었습니다. 실패 경로마다 "무엇이 없었는지 / 어떻게 고치는지" 두 문장을 붙이자 문의가 사라졌습니다.

자동화의 범위를 좁게 잡은 것도 잘한 선택이었습니다. AI로 요약 문장까지 생성하는 기능을 검토했지만, 사람이 검수해야 하는 결과물은 자동화의 이득이 크지 않았습니다. 대신 손으로 쓸 자리를 명확히 비워두는 쪽을 택했습니다.

테스트는 실제 저장소를 임시 디렉터리에 만들어 커밋을 쌓는 방식으로 짰습니다. git을 모킹하는 것보다 훨씬 빨리 신뢰가 생겼고, 실행 시간도 전체 3초 이내로 충분히 빨랐습니다.
