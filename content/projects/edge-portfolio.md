## 개요

지금 보고 있는 이 사이트입니다. "관리할 서버가 없는 포트폴리오"를 목표로 잡고, 프레임워크를 하나도 쓰지 않은 채 얼마나 멀리 갈 수 있는지 실험했습니다.

핵심 아이디어는 **콘텐츠와 상태를 분리한 하이브리드 모델**입니다. 작품 소개처럼 배포 시점에 이미 확정된 데이터는 리포지토리의 Markdown 파일로 두고 빌드할 때 HTML로 구워버립니다. 조회수·방명록처럼 런타임에만 알 수 있는 값만 D1에 남깁니다. 결과적으로 페이지 하나를 여는 데 필요한 DB 조회는 0회입니다.

## 주요 기능

- **단일 Worker 아키텍처** — `/api/*` 요청은 Worker가 직접 처리하고, 나머지는 `env.ASSETS.fetch()`로 정적 빌드 산출물에 넘깁니다. 배포 단위가 하나라 롤백도 하나입니다.
- **빌드 타임 콘텐츠 생성** — `content/projects/*.md` 파일을 파싱해 작품별 상세 HTML과 클라이언트 필터용 JSON 인덱스를 생성합니다. 작품을 추가하려면 md 파일 하나를 커밋하면 끝입니다.
- **클라이언트 사이드 검색·태그 필터** — 인덱스 JSON 하나만 받아 브라우저에서 필터링합니다. 검색어와 태그는 URL 쿼리에 동기화되어 그대로 공유할 수 있습니다.
- **조회수 카운터** — `sessionStorage` 가드로 세션당 한 번만 증가시키는 UPSERT. 카운트가 아직 안 왔거나 API가 죽어 있어도 페이지는 그대로 보입니다.
- **스팸 차단 3단** — Turnstile 서버 검증 + 입력 길이/형식 검사 + IP 해시 기반 레이트리밋(5분 1건). 원본 IP는 저장하지 않고 `SHA-256(IP + salt)`만 남깁니다.

## 배운 것

정적 생성의 경계를 어디에 그을지가 이 프로젝트의 거의 전부였습니다. 처음에는 작품 목록까지 D1에서 읽어오려 했는데, 그러면 매 요청마다 쿼리가 나가고 캐싱 전략이 복잡해집니다. "이 데이터가 배포와 무관하게 바뀌는가?"라는 질문 하나로 나누자 구조가 단순해졌습니다.

프레임워크 없는 MPA는 생각보다 불편하지 않았습니다. 헤더·푸터 마크업이 페이지마다 중복되지만, 그 대가로 하이드레이션도 라우터도 번들 분석도 필요 없습니다. 페이지 전환은 브라우저가 원래 잘하던 일입니다.

반대로 아쉬운 점은 공통 마크업의 드리프트입니다. 페이지 여섯 개의 헤더를 바이트 단위로 같게 유지하는 건 사람이 할 일이 아니라서, 다음 버전에서는 빌드 스크립트가 파셜을 주입하는 방식으로 옮기려 합니다.
