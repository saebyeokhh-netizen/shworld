---## 오늘 한 일

기획서(`docs/PRD.md`)를 읽고 학주학생학부모 프로젝트를 처음부터 세웠다. 빈 폴더에서 시작해 GitHub private 저장소 연결, 프로젝트 스캐폴딩, 공유 계약 정의, 그리고 4개 병렬 에이전트 투입까지 진행했다.

## 왜 "계약 먼저" 방식으로 갔는가

이 프로젝트는 규칙 엔진, AI, 화면 8개, 플레이 화면 7개 컴포넌트를 만들어야 하는 분량이다. 순차로 만들면 오래 걸리고, 그렇다고 병렬로 나누면 서로가 서로의 인터페이스를 기다리게 된다.

그래서 **작업을 나누기 전에 모듈 간 경계를 먼저 코드로 고정**했다.

- `src/game/types.ts` — 도메인 타입 전부. 카드·플레이어·트릭·라운드·게임 상태·액션·AI 시야.
- `src/game/constants.ts` — 규칙 수치 전부. 점수 배수, 보너스 점수, 방 설정 범위.
- `src/game/{deck,trick,scoring,engine}.ts` — 함수 시그니처만 채우고 본문은 `throw new Error('not implemented')`.
- `src/styles/tokens.css` — 색상·간격·타이포 토큰.
- `src/components/ui/` — 공통 UI 키트 11종.

시그니처가 먼저 있으니 엔진 구현자와 AI 구현자가 동시에 시작할 수 있다. 토큰과 UI 키트가 먼저 있으니 화면 담당 둘이 서로 다른 버튼을 만들 일이 없다.

## 규칙 해석에서 정한 것

기획서에 수치가 없어 직접 정한 항목이 둘 있다. 둘 다 `constants.ts` 한 곳에 모아두고 `ASSUMPTION` 주석을 달았으므로, 확정되면 그 파일만 고치면 된다.

1. **제압 보너스 점수.** 기획서는 "학주로 학생 잡으면 보너스, 학부모로 학주 잡으면 추가 보너스"라고만 적었다. 결과 목업의 `+70 = 2트릭×20 + 30` 표기에 맞춰 학생 제압을 30점으로 잡고, "추가 보너스"라는 표현을 따라 학주 제압을 50점으로 더 높게 뒀다.
2. **보너스 지급 조건.** 예측을 정확히 맞춘 플레이어에게만 보너스를 준다. 트릭테이킹 장르의 일반적 관례를 따랐다. `BONUS_REQUIRES_EXACT_BID` 를 `false` 로 바꾸면 예측 실패해도 보너스가 붙는다.

## 엔진을 순수 함수로 못박은 이유

`src/game/` 아래 모든 함수는 인자로 받은 상태를 변경하지 않고 새 상태를 반환한다. 난수도 `Math.random` 대신 시드 기반 생성기(`rng.ts`)만 쓴다.

당장은 테스트 재현성 때문이지만, 진짜 이유는 나중에 있다. 기획서 7절이 채택한 Playroom Kit은 **클라이언트(호스트)-authoritative** 모델이라 호스트가 계산한 결과를 다른 참가자가 그대로 받는다. 규칙 계산이 결정론적이지 않으면 검증할 방법이 없고, 손패 같은 히든 정보가 전역 상태로 새면 곧바로 치팅이 된다. 그래서 AI도 `AiView` 라는 별도 타입으로 자기 손패만 보게 막아뒀다.

## 병렬 작업 분할

서로 파일이 겹치지 않도록 4갈래로 쪼개 백그라운드 에이전트에 넘겼다.

| 담당 | 범위 |
|---|---|
| 규칙 엔진 | `src/game/{deck,trick,scoring,engine}.ts` 구현 + Vitest 테스트 |
| AI · 스토어 | `src/ai/bot.ts`, `src/store/gameStore.ts`, `src/lib/useCountdown.ts` |
| 비게임 화면 | `src/screens/*.tsx` — 스플래시·로그인·튜토리얼·홈·로비·프라이빗방·코인샵·스킨샵 |
| 플레이 화면 | `src/screens/game/*.tsx` — 플레이·입찰·결과·손패·트릭존·이모트 |

플레이 화면 담당에게는 스토어를 import하지 말고 **props로만 동작하는 프레젠테이션 컴포넌트**로 만들라고 지시했다. 스토어를 만드는 에이전트와 동시에 돌기 때문이다. 스토어 연결은 통합 단계에서 한다.

## 다음

에이전트 결과를 받아 통합하고, 타입체크와 테스트를 통과시킨 뒤 실제로 한 판이 돌아가는지 확인한다. 그 다음이 Playroom Kit 연동인데, 기획서가 최우선 확인 사항으로 꼽은 "손패를 player-private 상태로 분리할 수 있는가"를 먼저 검증해야 한다.

## 문제

화면은 다 만들어졌지만 **로비에서 무엇을 고르든 게임은 같은 판이 열렸다.** 플레이 화면이 `FALLBACK_CONFIG`(4인 · 15초 · 5라운드)로만 시작했기 때문이다. 인원 그룹, 턴 제한시간, 특수카드 장수를 고르는 UI 는 있는데 그 값이 엔진까지 가지 못했다.

## 어떻게 넘겼나

**라우터 state 로 넘긴다.** `navigate(ROUTES.game, { state: { config } })` 로 실어 보내고 플레이 화면이 `useLocation().state` 에서 읽는다.

스토어에 직접 밀어넣는 방법(로비에서 `startLocalGame()` 을 부르고 이동)도 있었지만 state 쪽을 택했다. 스토어는 메모리에만 있어서 새로고침하면 사라지지만 **history state 는 남기 때문**이다. `/game` 에서 새로고침해도 같은 설정으로 다시 시작한다. 그리고 나중에 Playroom 이 붙으면 "방 설정을 들고 방에 입장한다"는 흐름과도 모양이 맞는다.

변환은 `src/lib/gameConfig.ts` 한 곳에 모았다. 화면마다 `GameConfig` 를 조립하면 "매칭은 특수카드를 못 고른다" 같은 규칙이 여기저기 흩어지기 때문이다.

- `buildMatchConfig(sizeGroup, turnSeconds)` — 매칭 모드. 특수카드는 표준 룰 고정(PRD 4절)
- `buildPrivateConfig({ playerCount, turnSeconds, specialCards })` — 방장이 정한 값 그대로
- `isGameLaunchState(value)` — history 에 아무 값이나 들어올 수 있으므로(주소창 조작, 예전 버전이 남긴 state) 최소한의 형태 검사

## 정한 것들

**매칭 인원은 그룹 범위 안에서 뽑는다.** 매칭 탭은 인원을 정확히 고르지 않고 그룹(소규모 2~3인 / 중규모 4~5인 / 대규모 6~8인)만 고른다. 실제 인원은 매칭 결과라서, 매칭 서버가 붙기 전인 지금은 범위 안에서 무작위로 정하고 빈 자리를 봇으로 채운다.

**`maxRounds` 는 지정하지 않는다.** PRD 3절이 "최대 라운드 수 = 인원수에 따라 자동 계산"이라고 못 박았으므로 엔진의 덱 기준 계산에 맡긴다. 4인이면 16라운드짜리 긴 게임이 된다. `FALLBACK_CONFIG` 의 5라운드 제한은 로비를 거치지 않고 `/game` 으로 바로 들어왔을 때만 쓰는 맛보기 값으로 남겼다.

**같은 진입에서는 판을 다시 시작하지 않는다.** 진입 처리는 `location.key` 를 기억해 두는 방식으로 했다. history 항목마다 키가 달라서, 로비에서 새 설정으로 다시 들어오면 새 판이 열리고, 같은 진입 안에서는 리렌더가 몇 번 일어나도 판이 리셋되지 않는다.

**프라이빗 방 시작 버튼을 열어줬다.** 원래는 정원이 찰 때까지 시작을 막게 되어 있었는데, Playroom 연동 전이라 사람이 더 들어올 방법이 없어 버튼이 영영 눌리지 않았다. 빈 자리를 봇으로 채워 시작하되 버튼 문구로 그 사실을 밝히도록 했다("봇 1명과 함께 시작"). 연동 후 `disabled={missing > 0}` 로 되돌릴 자리라고 주석에 적어뒀다.

## 검증

단위 테스트 6개를 붙였다(총 146개 통과). 매칭 인원이 그룹 범위를 벗어나지 않는지 200회씩 돌려 확인하고, `isGameLaunchState` 가 쓰레기 값을 걸러내는지 확인한다.

브라우저에서도 확인했다.

- 대규모 + 10초 → 좌석 6자리로 시작
- 소규모 + 30초 → 좌석 2자리, 타이머 "30초" 표시
- 프라이빗 3인 → 방 화면에 "3인 · 턴 20초" 표기, 시작 버튼 "봇 1명과 함께 시작", 게임 좌석 3자리
- 콘솔 에러 0건

## 무엇을 만들었나

로비에서 "빠른 매칭 시작"을 누르면 곧장 게임이 열리던 것을, **대기 화면을 거쳐 인원이 모인 뒤 시작**하도록 바꿨다. 새 경로 `/matching` 과 화면 `src/screens/Matching.tsx` 가 그것이다.

목업이 없는 화면이라 PRD 4절의 규칙과 기존 디자인 톤만 가지고 구성했다. 화면에 남긴 정보는 셋이다 — **남은 대기 시간**(큰 숫자, 5초 이하는 빨간색으로 맥박), **모인 사람**(정원만큼 좌석을 그려두고 빈자리는 점선), **방 요약**(그룹·인원 범위·턴 시간). 하단에는 매칭 취소.

## 규칙은 PRD 의 "방식 A" 를 그대로

PRD 4절이 정한 매칭 규칙은 **유동 인원**이다.

- 대기시간(`MATCH_WAIT_SECONDS = 15`)이 지나면 **그때까지 모인 인원으로 자동 시작**한다. 정원을 채울 때까지 기다리지 않는다.
- 정원이 먼저 차면 기다릴 이유가 없으므로 즉시 시작한다("매칭 완료" 를 잠깐 보여주고 넘어간다).
- 다만 그룹 최소 인원에 못 미치면 게임이 성립하지 않으므로 최소치까지는 채운다. 대규모(6~8인)에서 15초 동안 4명만 모였다면 6명으로 시작한다.

이 판단을 `matchPlayerCount(sizeGroup, joined)` 라는 순수 함수로 떼어 두고 테스트를 붙였다. 화면 안 `useEffect` 에 묻어두면 "몇 명으로 시작하는가" 라는 게임 규칙이 UI 코드에 숨는다.

## 흉내 내는 부분과 진짜인 부분을 갈라뒀다

매칭 서버(Playroom)가 아직 없어서 **"들어오는 사람"은 이 화면이 흉내 낸다.** 0.7~3.2초 간격으로 한 명씩 늘린다.

그래서 연동 시 갈아끼울 자리와 그대로 둘 자리를 처음부터 갈라놨다. 흉내는 "인원이 하나 늘었다"는 이벤트를 만드는 `useEffect` 하나뿐이고, 카운트다운·정원 도달 즉시 시작·만료 시 인원 확정·게임 진입은 실제 참가 이벤트로 바꿔도 그대로 쓴다.

## 대기 화면의 얼굴과 게임의 얼굴을 맞췄다

대기 화면에서 "민준"이 들어왔는데 게임에는 다른 이름이 앉아 있으면 같은 방에 들어간 것처럼 보이지 않는다. 이름·아바타 색 배정 규칙이 스토어(`gameStore`) 안에만 있었기 때문에 생길 뻔한 문제라, 좌석 번호 → 표시 정보 변환을 `src/lib/opponents.ts` 의 `seatIdentity(index)` 로 빼고 양쪽이 같이 쓰게 했다.

## 그 밖에 정한 것

**게임으로 넘어갈 때 `replace: true` 를 쓴다.** 그러지 않으면 게임에서 뒤로가기를 눌렀을 때 이미 끝난 매칭 대기 화면으로 돌아가 카운트다운이 다시 돈다. 실제로 확인했고, 지금은 로비로 나간다.

**주소창으로 `/matching` 에 직접 들어오면 로비로 돌려보낸다.** 인원 그룹·턴 시간이 없으면 기다릴 대상 자체가 없다. history state 는 아무 값이나 들어올 수 있으므로 `isMatchWaitState` 로 형태를 검사한다.

**좌석 칸 수는 정원에 맞춘다.** 4칸 고정이면 3인 방일 때 왼쪽으로 쏠려 보인다.

## 검증

단위 테스트 5개 추가(총 151개 통과). `matchPlayerCount` 가 모인 인원을 그대로 쓰는지, 최소 인원 미달을 메우는지, 정원을 넘기지 않는지 확인한다.

브라우저에서 세 갈래를 모두 확인했고 콘솔 에러는 없다.

- **정원 도달 경로**: 소규모(2~3인) → 6.0초 만에 3자리로 시작 (15초를 기다리지 않음)
- **만료 경로**: 대규모(6~8인)에서 입장 간격을 최대로 고정 → 15.1초에 만료, 그 시점 인원이 최소치 미만이라 6자리로 시작
- **뒤로가기**: 게임에서 뒤로 → 대기 화면이 아니라 로비
- **직접 진입**: `/matching` 주소 입력 → 로비로 리다이렉트
