---## 처음에는 `<audio>` 로 틀었다 — 그리고 되돌렸다

효과음은 0.1초짜리라 통째로 펼쳐 메모리에 올려두고 쓴다. 음악은 한 곡이 2.4MB, 1분 20초라
같은 방식이면 펼치는 데만 28MB 를 쓴다. 그래서 `<audio>` 에 맡겨 흘려보내며 재생했다.

**안드로이드가 그것을 음악 앱으로 알아봤다.** 잠금화면에 재생 알림이 뜨고, 곡 제목 자리에
우리 사이트 주소가, 그 아래 재생/정지 버튼과 진행 막대까지 붙었다. 카드게임 배경음악에
그런 것이 붙을 이유가 없다.

그래서 **Web Audio 로 직접 트는 방식으로 바꿨다.** 효과음과 같은 장치를 쓰므로 잠금화면에
아무것도 뜨지 않는다.

### 메모리는 다시 구워서 줄였다

Web Audio 로 틀려면 곡을 통째로 펼쳐야 한다. 1분 20초 스테레오 44.1kHz 는 28MB, 두 곡이면
56MB — 폰에서 감당하기 어렵다.

그래서 펼친 뒤 **모노 22kHz 로 다시 구워** 4분의 1(7MB)로 줄이고 펼친 원본은 버린다.
배경음악은 아주 작게 깔리는 소리라 그 정도로 낮춰도 사람은 알아채지 못한다.
받는 파일은 여전히 mp3 그대로라 **다운로드는 2.4MB 그대로**다.

## 아주 작게 깐다

볼륨 **0.08**. 효과음이 0.3 언저리에서 우는 것에 견주면 4분의 1이다.

처음 들으면 "이게 들리나" 싶은 크기가 맞다. 배경음악이 크면 카드 소리가 묻히고, 그러면
사람들은 **소리를 통째로 꺼버린다.** 있는 줄 모르게 깔리는 편이 낫다.

## 스위치를 따로 뒀다

설정에 **배경음악** 항목을 새로 만들었다. 효과음과 묶지 않은 이유 —

효과음은 지금 무슨 일이 일어났는지 알려주지만 **음악은 분위기만 만든다.** 지하철이나
사무실에서는 음악만 끄고 효과음은 남기고 싶은 사람이 많다. 하나로 묶어두면 그런 사람은
결국 소리를 통째로 꺼버린다.

옛 저장값에는 이 항목이 없다. 없으면 기본값(켬)으로 읽는다.

## 곡은 둘뿐이다

**판이 도는 동안**과 **그 밖의 모든 곳**. 화면마다 다른 곡을 틀면 상점에 잠깐 들렀다
오는 동안에도 음악이 두 번 바뀌어 정신이 없다.

곡을 바꿀 때는 0.9초에 걸쳐 겹친다. 뚝 끊고 다른 곡을 시작하면 화면 전환이 거칠어진다.

껍데기(`RootLayout`)에 두었다. 화면마다 붙이면 홈에서 상점으로 갈 때마다 **같은 곡이
처음부터 다시 시작한다.**

## 브라우저가 막을 때

사람이 화면을 한 번 건드리기 전에는 소리를 낼 수 없다. 재생이 거절당하면 조용히 넘어가고
**다음 조작 한 번을 기다렸다 다시 시도**한다. 버튼을 한 번만 누르면 그때부터 흐른다.

## 다른 앱을 보는 동안에는 멈춘다

이게 없으면 카카오톡을 보는 내내 우리 음악이 흐른다. 돌아오면 다시 튼다 — 그때는 이미
화면을 건드린 뒤라 브라우저가 막지 않는다.

## 확인 — 쓰지 않는 곡은 받지 않는다

4.8MB 짜리 둘을 첫 화면에서 다 받으면 안 된다. 실제 빌드로 확인했다.

```
홈    → home.mp3 만
게임  → home.mp3, game.mp3
```

개발 서버에서는 둘 다 받는 것처럼 보였는데, 그건 Vite 가 모듈을 훑느라 생긴 요청(`?import`)
이었고 실제 빌드에는 없다. **개발 서버에서 본 것을 그대로 믿으면 안 된다.**

## 무슨 일이 있었나

"다른 앱으로 가면 30초 뒤 배경음악을 끈다" 를 넣었는데 **전혀 꺼지지 않았다.** 두 번
고쳤는데도 그대로였다.

## 왜 못 찾았나 — 잘못된 추론

막는 장치를 둘 걸어두었다. 오디오 시계로 볼륨을 줄이고, 보통 시계로 재생을 멈춘다.
서로 다른 시계라 한쪽이 멈춰도 다른 쪽이 듣는다. 그런데도 소리가 났으니 **둘을 예약하는
코드가 애초에 안 불린 것**이라고 판단했고, 신호(`visibilitychange`)를 못 받는 문제로
좁혔다. 그래서 `blur`·`pagehide` 까지 듣게 했다. 그래도 안 꺼졌다.

추론 자체는 논리적이었지만 전제가 틀렸다. **장치가 불리기는 했는데, 불린 그 자리에서
소리를 도로 켜고 있었다.**

## 진짜 원인

`src/lib/sound.ts` 의 소리 장치를 가져오는 함수가 이랬다.

```ts
function getContext(): AudioContext | null {
  ...
  if (context.state === 'suspended') void context.resume();   // ← 이것
  return context;
}
```

자동재생 정책 때문에 멈춰 있는 장치를 깨우려고 넣은 줄이다. 그런데 **브라우저는 다른 앱으로
넘어가면 소리 장치를 스스로 멈춘다.** 그 상태에서 우리 코드가

```ts
function scheduleAwayStop(): void {
  const ctx = getAudioContext();   // ← 여기서 깨어난다
  ...
}
```

를 부르는 순간 멈춰 있던 장치가 **도로 깨어났다.** 끄려는 코드가 켜고 있었던 셈이라,
끄는 방법을 아무리 정교하게 만들어도 소용이 없었다. `stopMusic()` 도 같은 함수를 부르므로
**이 문제는 30초 유예를 넣기 전부터 있었다** — 즉 배경음악은 처음부터 다른 앱에서 계속
흐르고 있었다.

## 고친 방법

### 1. 일부러 멈춰둔 동안에는 깨우지 않는다

판단을 함수로 떼어 시험으로 굳혔다.

```ts
export function shouldWake(away: boolean, state: AudioContextState): boolean {
  return !away && state === 'suspended';
}
```

### 2. 볼륨을 줄이는 대신 장치를 통째로 멈춘다

볼륨을 줄이려면 **끄는 코드가 제때 불려야** 한다. 신호가 안 오는 환경이 있는 이상 그 방법은
믿을 수 없다. 장치를 멈추면 음악도 효과음도 그 자리에서 전부 조용해진다.

덤으로 30초 유예가 필요 없어졌다. 장치는 **멈춘 자리를 기억**하므로, 돌아오면 끊겼던 곳에서
이어진다. 잠깐 카카오톡에 다녀와도 곡이 처음으로 되돌아가지 않는다 — 유예를 두려던 이유가
바로 그것이었는데, 이 방법에서는 공짜로 따라온다.

### 3. 신호는 셋 다 듣는다

설치한 앱에서 `visibilitychange` 를 놓치는 경우가 실제로 있으므로 `blur`·`pagehide` 도
함께 듣는다. `setAudioAway` 는 같은 값으로 여러 번 불러도 아무 일도 하지 않아 겹쳐도 탈이 없다.

## 남긴 교훈

**"끄는 코드가 안 불렸다" 와 "불렸는데 효과가 없었다" 를 가르지 않고 앞엣것으로 단정했다.**
장치를 가져오는 함수 안에 부작용(깨우기)이 들어 있었기 때문인데, 그 함수를 한 번도 읽지
않은 채 두 번을 고쳤다. 고치기 전에 **부르는 쪽이 아니라 불리는 쪽**을 읽었어야 했다.
