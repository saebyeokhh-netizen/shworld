---## 무엇이 문제였나

개인정보 처리방침 8절에는 이미 이렇게 적혀 있었다.

> 이 서비스는 **만 14세 이상**만 이용할 수 있습니다.

그런데 확인하는 절차가 없었다. **적어두고 지키지 않는 문장은 안 적은 것보다 나쁘다** —
분쟁이 생기면 "알고도 방치했다" 는 근거가 된다.

근거 조문은 개인정보 보호법 제22조의2 다. 만 14세 미만의 개인정보를 처리하려면 법정대리인
동의가 필요한데, 우리는 그 동의를 받을 방법이 없다. 그래서 **동의를 받는 대신 계정을
만들지 않는** 쪽을 택했다.

## 생년월일을 저장하지 않는다

이 기능에서 제일 중요한 결정이다.

필요한 것은 "만 14세 이상임을 확인했다" 는 사실이지 생년월일 자체가 아니다. 최소수집
원칙(제3조 제1항)에 따라 생년월일은 계산하는 동안만 쓰고 버린다. DB 에 남는 것은 열
하나뿐이다.

```sql
ALTER TABLE users ADD COLUMN age_checked_at TEXT;
```

NULL 은 "아직 확인 안 함" 이다. 이 기능이 생기기 전에 가입한 사람도 여기 걸려서, 다음에
앱을 열 때 확인 화면을 한 번 거친다. 확인을 안 한 계정을 예외로 두면 법이 요구하는 것을
못 지킨 채로 남는다.

**저장하지 않은 정보는 유출될 수도 없다.**

## 막히더라도 게임까지 막지 않는다

만 14세 미만이면 계정을 만들지 않지만, **연습 게임은 그대로 열어 둔다.** 아이를 내쫓는
것이 목적이 아니라 아이의 개인정보를 갖지 않는 것이 목적이다. 차단 화면에서 바로
연습 게임으로 가는 버튼을 준다.

## 만 나이는 한국시간으로 센다

서버는 UTC 로 돈다. 그대로 세면 **생일 당일 오전 9시 전까지 아직 생일이 아닌 것으로
계산된다.** 생일에 가입하려는 사람이 하루를 더 기다리게 된다. 순위판이 주 경계를 KST 로
자르는 것과 같은 이유이고, 같은 함정이다.

테스트로 박은 것들:

| 경우 | 왜 |
| --- | --- |
| 생일 당일 자정(KST) | UTC 로 세면 13세가 되어 막힌다 |
| 2월 29일생, 평년 3월 1일 | 생일이 지난 것으로 봐야 한다 |
| `2001-02-29` | 없는 날. Date 가 3월 2일로 넘겨버려 나이가 조용히 어긋난다 |
| 만 14세 되는 날 / 하루 전 | 경계에서 한 칸 밀리면 안 된다 |

## 화면이 순서를 지키는 것과 강제되는 것은 다르다

문지기는 껍데기(`RootLayout`)에 한 번만 붙인다. 화면마다 거는 문(`RequireAuth`)에 넣으면
**화면을 옮길 때마다** 로그인 확인을 다시 기다리게 된다.

그리고 화면만으로는 부족해서 서버에서도 막는다. 확인 안 한 계정은 닉네임 저장과 전적
저장이 403 이다. 이 둘이 실제로 개인정보를 쓰는 지점이다.

읽을거리(처리방침·소개·게임 설명)와 연습 게임은 확인 전에도 열어둔다. **나이를 왜 묻는지
적어둔 문서를 못 읽게 하면 앞뒤가 맞지 않는다.**

## 겸사겸사 고친 것 — 탈퇴가 다 안 지우고 있었다

미성년 확인에 걸리면 계정을 지우는데, 기존 `deleteAccount` 가 **초대(`invites`)와 사과
내역(`apple_ledger`)을 남기고** 있었다. 본인이 누르는 탈퇴에서도 마찬가지였다. 법이
요구하는 삭제로도 쓰이게 됐으니 한 표라도 빠지면 "동의 없이 계속 가지고 있는 정보" 가
남는다. 두 줄을 더했다.

## 확인 직후 되돌려보내지던 문제

`useAuth` 는 부르는 곳마다 따로 상태를 들고 있다(공유 컨텍스트가 아니다). 확인 화면에서
`setUser` 를 해도 껍데기의 문지기가 든 것은 확인 전 상태 그대로라, 넘어가자마자 도로
확인 화면으로 튕겼다.

계정마다 한 번뿐인 일이라 **주소를 통째로 다시 여는** 쪽을 택했다. 상태를 공유하는 장치를
새로 만드는 것보다 간단하고 어긋날 여지가 없다.

## 배포는 2026년 9월 2일

**처리방침 새 판이 시행되는 날에 맞춘다.** 그 판에 연령 확인 내용을 이미 적어두었으므로,
문서에 적힌 날부터 실제로 확인이 시작되면 문서와 코드가 어긋나는 구간이 생기지 않는다.
아래 "남은 판단" 에 적은 공지 시점 문제도 이것으로 함께 풀린다.

D1 마이그레이션은 되돌리기 어려워서 그날까지 코드만 올려둔다. 적용은 다음과 같다.

```
cd server
npx wrangler d1 migrations apply schoolking --remote
npx wrangler deploy
```

**적용하는 순간 기존 계정도 확인 화면을 한 번 거친다.**

## 처리방침 공지 시점 — 시행일에 맞추는 것으로 정리됐다

시행 대기 중인 판(2026년 9월 2일 시행, 8월 26일 공지)에 연령 확인 항목을 함께 적었다.
공지보다 늦게 적은 내용이라 엄밀히는 공지 날짜를 다시 잡아야 하나 싶었는데, **배포를
시행일에 맞추기로 하면서 문제가 사라졌다** — 확인을 시작하는 날과 그 사실이 적힌 문서가
효력을 갖는 날이 같아진다.
