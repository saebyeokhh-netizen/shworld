---이용자가 "매칭하기 들어가면 바로 AI랑 매칭된다" 고 알렸다. 코드를 읽어보니 **자동으로 AI 와
붙이는 길은 없었다.** 15초 뒤 "아직 상대가 없어요" 를 물을 뿐이었다. 그런데 실제로 돌려보니
정말로 그런 일이 났다 — 혼자 매칭에 들어갔는데 1초 만에 게임 화면으로 넘어갔다.

## 진짜 원인 — 방이 판을 영원히 들고 있었다

방 서버(Durable Object)가 판을 `KEY_HOST` 로 저장소에 넣고, **새로 들어온 사람에게 그대로
내려주고 있었다.** 새로고침한 사람이 자기 판으로 돌아오게 하려고 만든 길인데, 그 길에는
"이 사람이 저 판에 있던 사람인가" 를 묻는 대목이 없었다.

그래서 이렇게 됐다.

1. 누군가 매칭 방에서 판을 시작한다
2. **그 방에는 판이 영원히 남는다**
3. 나중에 매칭을 누른 사람이 그 방에 들어가면 옛 판이 그대로 뜬다
4. 원래 있던 사람들은 이미 나갔으니 AI 가 대신 둔다 → **"매칭했더니 AI가 나왔다"**

빈 방을 치우는 사람이 아무도 없었다는 것이 핵심이다. Durable Object 는 저장한 것을 스스로
버리지 않는다.

## 고친 방법 — 다음 사람이 들어올 때 치운다

알람으로 치우는 방법도 있지만 **알람은 이미 판 진행에 쓰고 있어서** 겹치면 서로를 지운다.
그래서 "들어올 때 확인한다" 로 했다. 버리는 경우는 둘이다.

- **아무도 없던 시간이 60초를 넘겼다** — 다들 떠난 판은 이어갈 사람이 없다
- **판이 끝났는데 들어온 사람이 그 판에 없던 사람이다** — 끝난 판을 남에게 보여줄 이유가
  없다. 그 판에 있던 사람은 새로고침해도 결과를 다시 보게 남겨둔다

여기에 하나를 더 뒀다. **남이 두고 있는 판에는 끼어들 수 없다(409).** 치우고도 판이 남아
있다는 건 지금 진행 중이라는 뜻이라, 그 자리에 없던 사람은 아예 들여보내지 않는다.
빠른 매칭처럼 정해진 코드로 모두가 같은 문을 두드리는 경우에 특히 필요했다.

### 테스트가 잡아낸 실수

처음에는 "사람이 들어왔으니 빈 방이 아니다" 며 접속 처리 앞머리에서 빈 방 표시를 지웠다.
그런데 **문 앞에서 거절당한 사람도 그 자리를 지나간다.** 판이 도는 방을 누가 계속 두드리면
그때마다 시계가 0 으로 돌아가, 아무도 없는 방이 영영 낫지 않았다. 65초를 기다려도 그대로인
것을 보고 알았다. 정말로 들여보낸 뒤에 지우도록 옮겼다.

## 그리고 매칭 자체를 한 자리로

원래 하려던 일이다. 인원 그룹 셋 × 턴 시간 셋 = **대기열이 아홉 갈래**였다. 하는 사람이
아홉 명인데 방이 아홉 개면 둘이 같은 칸에 설 확률이 없다시피 하다. 고르는 것을 전부 없앴다.

| | 전 | 후 |
|---|---|---|
| 고르는 것 | 인원 그룹 · 턴 시간 | **없음** |
| 턴 시간 | 10 / 15 / 30초 | 10초 고정 |
| 인원 | 2~3 / 4~5 / 6~8 | 2~8인 |
| 대기열 | 아홉 갈래 | 하나 |
| 홈에서 | 로비를 거쳐 설정 | **곧장 대기 화면** |

시작 규칙도 바꿨다. 둘 이상 모이고 **새로 들어오는 사람이 3초간 없으면** 10초를 세고
시작한다. 그 사이에 누가 들어오면 **처음부터 다시** 센다 — 한 명이라도 더 끼워 주는 편이
판이 재밌고, 문 앞에서 닫히는 경험을 주지 않는다. 정원(8명)이 차면 곧바로 센다.

혼자 30초가 지나면 묻는다. **"같이 할 사람 찾으러 가기"(오픈채팅)** 와 **"AI와 연습하기"**
둘 중에 고르고, "계속 기다리기" 는 작게 남겼다. 예전에는 AI 가 제일 큰 버튼이었는데,
사람과 하려고 온 사람에게 줄 첫 답이 아니다.

방이 차 있으면 옆방(`MATCH2`, `MATCH3`…)을 두드린다. 모두 같은 순서로 두드리므로 결국 같은
방에서 만나고, 빈 방은 서버가 치우므로 번호가 계속 늘어나지 않는다.

## 확인

`tsc` 통과, 테스트 **285개** 통과, 빌드 통과.

**서버** — 로컬 방 서버에 붙여 직접 확인했다.

| | |
|---|---|
| 판이 도는 방에 남이 들어오기 | 409 로 막힘 ✅ |
| 그 판에 있던 사람이 돌아오기 | 들어가고 판 상태도 받음 ✅ |
| 모두 나간 뒤 65초 → 새 사람 | 깨끗한 방, 먼저 온 사람이 방장 ✅ |

**화면** — 브라우저 창 두 개로 확인했다.

```
가 혼자 대기 → 1명
나 입장      → 2명
3초 조용      → "곧 시작합니다" 10초 (두 화면 똑같이)
14초         → 둘 다 게임 화면
```

혼자 남았을 때의 물음도 눌러 봤다 — 오픈채팅, AI 연습, 계속 기다리기 셋이 의도한 순서로 뜬다.

## 곁다리 — 브라우저가 자꾸 죽던 것도 이 버그였다

확인 중에 `/matching` 만 열면 브라우저 탭이 죽었다. 다른 화면은 멀쩡했다. 원인은 **옛 판으로
끌려 들어가 무거운 게임 화면이 통째로 그려졌기** 때문이었다. 이 PC 는 여유 메모리가 2GB 안팎
이라 그걸 버티지 못했다. 버그를 고치니 그대로 없어졌다.

## 배포 순서에 주의

**서버를 먼저 올려야 한다.** 화면만 먼저 올라가면 방은 여전히 오염된 채이고, 옆방을 두드리는
길(409)도 서버가 없으면 열리지 않는다.

```bash
cd server && npx wrangler deploy
```

그 다음에 `main` 에 합치면 화면이 자동으로 배포된다.

## 덧붙임 — 시작을 시간이 아니라 **사람**이 정하게

처음에는 "둘 이상 모이고 3초간 조용하면 10초를 세고 시작" 이었다. 그런데 그러면 **화면을
보고 있지 않던 사람이 첫 라운드를 통째로 날린다.** 매칭이 붙는 순간을 아무도 모른 채 카드가
깔리기 때문이다.

그래서 각자 **"준비" 를 누르게** 바꿨다. 모두 누르면 10초를 세고 시작한다. 시작 시점이
**모두가 아는 시점**이 된다.

- 준비 버튼은 **모두에게** 있다. 프라이빗 방은 방장이 시작을 쥐고 나머지가 준비를 누르지만,
  매칭에는 "방을 연 사람" 이라는 개념이 없다. 누가 시작 권한을 쥐는지 이용자는 알 수도 없고
  알 필요도 없어서, 모두가 같은 것을 누른다
- 세는 도중에 누가 들어오면 그 사람은 아직 준비가 아니므로 **카운트다운이 멈춘다.**
  문 앞에서 닫히는 경험을 주지 않으려는 것이다
- 자리마다 `준비`/`대기` 를 적고 아직인 사람은 아바타를 흐리게 한다. 누구를 기다리는지
  보이지 않으면 "왜 안 시작하지" 가 된다

준비 신호는 이미 있던 길(`broadcast`)과 모양(`ReadyMessage`)을 그대로 쓴다. 서버는 뜻을
모르고 전달만 한다. **저장하지 않는 것도 그대로다** — 준비는 이 방, 이 순간에만 뜻이 있는
값이라 나갔다 들어오면 다시 누르는 것이 맞다. 대신 명단이 바뀔 때마다 내 상태를 한 번 더
알려서, 새로 들어온 사람의 화면도 같아지게 한다.

`MATCH_QUIET_SECONDS`(조용한 3초)는 필요가 없어져 지웠다.

### 확인

창 두 개로 눌러가며 확인했다.

| | |
|---|---|
| 둘 접속, 아무도 준비 안 함 | 안 셈 ✅ |
| 한 명만 준비 | **여전히 안 셈** ✅ |
| 둘 다 준비 | "곧 시작합니다" 10초 (두 화면 똑같이) ✅ |
| 10초 뒤 | 둘 다 게임 화면, 판 진행 ✅ |
