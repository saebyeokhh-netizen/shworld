---애드센스에서 **정책 위반** 통보를 받았다. 문구는 이랬다.

> **게시자 콘텐츠가 없는 화면에 Google 게재 광고**
> - 콘텐츠가 없거나 가치가 낮은 콘텐츠를 포함한 화면
> - 아직 준비 중인 화면
> - 알림, 이동 또는 기타 행동 목적으로 사용되는 화면

흔한 "저품질 콘텐츠" 반려가 아니다. **광고가 실리면 안 되는 화면에 광고 코드가 실렸다**는
지적이고, 실제로 그랬다.

## 원인 — SPA 에서 index.html 은 모든 화면이다

광고 스크립트를 `index.html` 머리에 넣어 두었다. 보통의 웹사이트라면 페이지마다 HTML 이
따로 있으니 그 페이지에만 실린다. 그런데 이 앱은 **화면이 바뀌어도 같은 HTML 한 장**을 계속
쓴다. 그래서 거기 넣은 광고 코드는 모든 화면을 따라다닌다.

구글이 금지한 유형과 우리 화면이 하나씩 맞아떨어졌다.

| 우리 화면 | 무엇인가 | 금지 유형 |
|---|---|---|
| 스플래시(`/`) | 로고만 1.8초 보여주고 넘어감 | 이동 목적 |
| 로그인(`/login`) | 로그인 버튼뿐 | 행동 목적 |
| 로그인 콜백(`/auth/callback`) | "로그인 중…" 한 줄 | 내용 없음 |
| 매칭 대기(`/matching`) | 사람을 기다림 | 대기 화면 |

**게다가 스플래시가 우리 정식 주소(canonical)다.** 심사자가 제일 먼저 본 화면이 하필
"로고 하나 + 광고 요청" 이었다.

그리고 스크립트만 실린 것도 아니었다. `adConfig({ preloadAdBreaks: 'on' })` 가 함께 있어서
**페이지가 열리는 순간 광고를 실제로 요청**했다. 미리 받아둬야 누르는 순간 바로 뜬다는
이유로 넣은 줄인데, 그 "페이지" 가 모든 화면이었던 것이다.

문제가 아니었던 것: 광고를 **부르는** 자리(`showRewardedAd`, "광고 보고 사과 받기" 버튼)는
정책에 맞았다. 잘못은 부르는 곳이 아니라 **싣는 곳**이었다.

## 고친 방법 — 필요한 순간에만 붙인다

`index.html` 에서 스크립트를 걷어내고, `loadAdScript()` 를 만들어 **광고를 실제로 볼 수 있는
자리에서만** 부르게 했다. 지금 그 자리는 황금 사과를 받는 곳 하나뿐이라, 호출도
`useAdReward` 훅 안에 한 번만 두었다 — 이 훅이 도는 화면이 곧 광고가 허용되는 화면이다.

### 검사가 잡아준 것 — 홈은 사과 창을 미리 그려둔다

고치고 확인해 보니 **스플래시에서도 여전히 광고 요청이 나갔다.** 스플래시가 1.8초 뒤 홈으로
넘어가는데, **홈이 사과 창(AppleSheet)을 닫힌 채로 미리 그려두기** 때문이었다. 창이 닫혀
있어도 그 안의 훅은 돌고, 훅이 돌면 스크립트가 붙는다.

그래서 `useAdReward(apples, active)` 로 바꿔 창이 정말 열렸을 때만 붙게 했다. 화면에 안 보인다고
코드가 안 도는 것은 아니다 — 이 프로젝트에서 두 번째로 겪는 종류다(첫 번째는 손패였다).

## 확인

`tsc` 통과, 테스트 285개 통과. 빌드 결과물에 `googlesyndication` 문자열이 **0건**.

브라우저에서 화면별로 광고 요청이 나가는지 가로채어 셌다.

| 화면 | 광고 스크립트 요청 |
|---|---|
| 스플래시 → 홈 | 안 함 ✅ |
| 로그인 | 안 함 ✅ |
| 매칭 대기 | 안 함 ✅ |
| 게임 | 안 함 ✅ |
| 전적 | 안 함 ✅ |
| 홈(사과 창 닫힘) | 안 함 ✅ |
| **사과 충전 화면** | **함** ✅ |
| **홈에서 사과 창 열기** | **함** ✅ |

## 아직 남은 것 — 첫인상

정식 주소로 들어오면 2초 만에 "로고 → 로그인하세요" 가 뜬다. 이번 통보의 직접 사유는
아니지만 **"콘텐츠가 없는 화면"** 이라는 지적과 같은 결이라, 재심사에서 또 걸릴 수 있다.
스플래시에 게임 소개를 몇 줄 넣거나 소개 화면으로 보내는 것을 검토할 만하다. 제품 결정이라
따로 정하기로 했다.

## 재심사 전에 확인할 것

1. `curl -s https://shworld.cloud/ | grep googlesyndication` → **아무것도 안 나와야 한다**
2. `curl -s https://shworld.cloud/ads.txt` → 한 줄이 그대로 나와야 한다 (이건 남긴다)
3. 시크릿 창으로 열어 새 HTML 이 내려오는지 — 서비스 워커가 옛 것을 들고 있을 수 있다
4. 사과 창을 열어 "광고 보고 받기" 가 여전히 동작하는지 (승인 전이라 "광고가 아직
   연결되지 않았어요" 가 뜨면 정상)
5. 그 다음에 애드센스에서 "문제를 수정했음을 확인합니다" → 검토 요청

## 덧붙임 — 첫 화면도 함께 고쳤다

광고 코드 위치가 직접 사유였지만, **정식 주소가 로고만 1.8초 보여주다 넘어가는 화면**이라는
것도 같은 결의 문제였다. 심사자가 제일 먼저 보는 자리이기도 하다. 그래서 첫 화면을 **읽을
것이 있는 소개 화면**으로 바꿨다.

- 그림은 화면을 덮는 배경에서 **위쪽 머리말 띠**로 물렸다
- 한 줄 소개 + **시작하기** 버튼을 위에 둔다. 아래 설명은 읽고 싶은 사람을 위한 것이지
  시작하려는 사람을 가로막으라고 있는 것이 아니다
- 세 꼭지를 붙였다 — 어떤 게임인가요 / 카드 셋이 서로 물고 물려요 / 어떻게 즐기나요
- **자동으로 넘어가지 않는다.** 자동으로 넘기면 읽을 것을 둔 의미가 없다

### 이미 하던 사람은 이 화면을 안 본다

매니페스트의 `start_url` 을 `/home` 으로 옮겼다. 홈 화면에 설치한 앱은 곧바로 게임으로
들어간다. 이 화면은 **처음 오는 사람과 검색·심사가 보는 자리**다.

파일 이름과 라우트 상수(`ROUTES.splash`)는 그대로 뒀다. PRD 5-1 이 이 이름을 쓰고 있어서,
하는 일이 바뀌었다고 이름까지 바꾸면 문서와 코드가 갈린다 — 카드 식별자를 그대로 둔 것과
같은 이유다.

서비스 워커 캐시를 v14 로 올렸다. 첫 화면과 매니페스트 둘 다 **파일 이름은 그대로인 채
내용만** 바뀌어서, 올리지 않으면 이미 설치한 사람에게 옛 화면이 계속 나온다.

### 확인

첫 화면에서 자동 이동이 없고(주소가 `/` 그대로), 본문 글자가 400자 넘게 있고, 세 꼭지가
모두 그려지고, **광고 요청은 여전히 0건**이다. "시작하기" 를 누르면 `/home` 으로 간다.

> "또 이런 게 왔네 ㅠㅜ 어쩐담"

애드센스가 `shworld.cloud` 를 **주의 필요**로 돌렸다. 사유 둘.

1. 게시자 콘텐츠가 없는 화면에 Google 게재 광고
2. **가치가 별로 없는 콘텐츠**

## ①은 이미 고쳐져 있었다

8월 28일에 광고 코드를 모든 화면에서 걷어내고, 광고를 실제로 보는 순간에만 붙게 바꿨다
(`rewardedAd.ts` 의 `loadAdScript`). 지금 사이트 첫 HTML 에 광고 코드가 **0개**인 것을 확인했다.

## ②의 원인 — 글이 없어서가 아니었다

```
심사 로봇이 각 주소에서 읽는 글자 수
  /          0자
  /guide     0자   ← 게임 방법 2,200자가 있는데도
  /privacy   0자   ← 처리방침 4,200자가 있는데도
  /about     0자
```

**로봇 눈에 안 보였다.** 이 앱은 빈 껍데기 HTML 을 먼저 주고 자바스크립트가 글자를 채운다.
사람 눈에는 멀쩡한데 로봇에게는 모든 페이지가 백지 한 장이다.

준비해 둔 `/m-hairsalon` 이전 계획도 이것부터 안 고치면 소용없었다 — 루트에 포트폴리오를
놔도 그것 역시 백지로 보일 테니까. (다행히 포트폴리오는 진짜 정적 HTML 이라 4,300자가
그대로 보인다.)

## 한 것

### 1. 게임을 `/m-hairsalon` 아래로 — 다시 얹었다

2026-08-27 에 준비해 둔 브랜치가 있었지만 **main 이 130 커밋 앞서 있었다.** 그대로 합치면
그동안 만든 것이 통째로 날아간다. 같은 변경을 지금 코드에 다시 적용했다.

한 칸이 붙는 것뿐인데 그 칸을 모르는 자리가 아홉이다: vite base/outDir, 라우터 basename,
서비스 워커 등록 경로와 내부 경로, 매니페스트 넷, canonical/og, `_redirects`, `APP_URL`.

예전 계획에 없던 것 하나를 더 찾았다. **`emptyOutDir` 는 자기 출력 폴더만 비운다.** 앱이
`dist/m-hairsalon/` 으로 내려가면 그 전에 만들어진 옛 결과물이 `dist/` 맨 위에 그대로 남아,
**사이트 맨 위에서 철 지난 게임이 열린다.** 거기는 이제 포트폴리오 자리다. 빌드 전에
`dist/` 를 통째로 비우게 했다.

### 2. 백지 고치기 — 두 번 만들었다

**첫 번째 시도(실패).** 배포 빌드에서 헤드리스 브라우저를 띄워 각 경로를 그리게 했다. 로컬
에서는 완벽했다(0자 → 9,600자). **Cloudflare Pages 미리보기 빌드가 실패했다.**

남의 빌드 환경에 브라우저를 설치해 띄우는 일은 통제할 수 없는 자리가 너무 많다 — 내려받기,
시스템 라이브러리, 시간 제한. 게다가 그게 깨지면 **배포 전체가 멈춘다.** 심사를 통과하려고
만든 장치 때문에 배포가 막히는 것은 바꿔치기가 나쁘다.

**두 번째(성공).** 무거운 일은 사람 손이 닿는 자리에서 미리 한다.

- `npm run prerender:snapshot` — 내 기기에서 브라우저로 그려 `prerender/*.json` 에 담는다.
  **저장소에 커밋한다**
- 배포 빌드는 `tools/apply-prerender.mjs` 가 Node 기본 기능만으로 그것을 새 HTML 에 심는다

**담아 두는 것은 `#root` 안의 알맹이와 제목뿐이다.** 완성된 HTML 을 통째로 저장하면 빌드
자산 이름의 해시(`index-BvBz9Lpv.js`)까지 굳어서, 다음 빌드에서 해시가 바뀌는 순간 **없는
파일을 부르는 죽은 페이지**가 된다. 껍데기는 그때그때 새로 빌드된 것을 쓴다.

알맹이가 낡을 수는 있다. 게임 방법 글을 고치고 스냅샷을 다시 안 뜨면 로봇이 읽는 글이
옛것이 된다. **사람이 보는 쪽은 자바스크립트가 새로 그리므로 틀린 내용이 보이지는 않는다.**
스냅샷은 저장소에 있어 눈으로 볼 수 있고 커밋 기록에도 남는다.

## 확인 — 실제 배포에서

미리보기 배포(`0d7a837d.schoolking.pages.dev`)에서 리다이렉트를 따라가 잰 값이다.

| 경로 | 전 | 후 |
|---|---:|---:|
| `/m-hairsalon/` | 0자 | **1,132자** |
| `/m-hairsalon/guide` | 0자 | **4,700자** |
| `/m-hairsalon/privacy` | 0자 | **6,970자** |
| `/m-hairsalon/about` | 0자 | **2,361자** |

빗금 없는 주소(`/guide`)는 308 로 빗금 있는 주소로 넘긴다 — 로봇도 따라간다.

## 아직 안 한 것

**`main` 에 합치지 않았다.** 합치는 순간 배포되면서 `shworld.cloud/` 가 잠깐 안 열린다.
포트폴리오 워커와 순서를 맞춰야 한다. 절차는 `DEPLOY.md` 에 적었다.

**사람이 해야 하는 것 하나** — Cloudflare 대시보드에서 Pages 커스텀 도메인
(`shworld.cloud`, `www.shworld.cloud`) 을 뗀다. Pages 커스텀 도메인은 호스트 이름 전체를
가져가 경로를 나눌 수 없고, wrangler 로는 못 지운다.

포트폴리오 저장소(`C:\project\shworld`)에는 루트 라우트를 넣어 뒀다. 아직 배포하지 않았다 —
게임보다 먼저 올리면 게임 주소가 포트폴리오로 넘어간다.

# 전환 실행 (같은 날 오후)

## 예상이 틀린 곳 — 커스텀 도메인은 뗄 필요가 없었다

"Pages 커스텀 도메인이 호스트 전체를 가져가니 먼저 떼야 한다" 고 적어 두었는데 **아니었다.**

워커를 하나 올려 시험했다. `shworld.cloud/*` 를 Pages 가 잡고 있는 상태에서
`shworld.cloud/m-hairsalon*` 라우트를 올리자 **그 경로만 워커로 왔다.** 워커 라우트가
앞선다. 그리고 Pages 에 붙어 있던 커스텀 도메인은 `www.shworld.cloud` 하나뿐이었고, 맨
주소는 커스텀 도메인이 아니라 DNS 로 Pages 를 보고 있었다. 뗐으면 www 로 들어오던 사람만
잃을 뻔했다.

**추측으로 지우지 않고 시험한 것이 남는 일이었다.**

## 찾은 것 — 사이트가 스스로 "색인하지 말라" 고 말하고 있었다

확인하다가 나왔다.

```
shworld.cloud       →  x-robots-tag: noindex
www.shworld.cloud   →  x-robots-tag: noindex
```

Cloudflare Pages 가 `*.pages.dev` 응답에 붙이는 헤더인데 커스텀 도메인까지 달고 나갔다.
워커가 서빙하는 주소에는 없다. **백지인 데다 색인하지 말라고까지 하는 사이트**였던 셈이다.

- 맨 위는 포트폴리오 워커가 직접 서빙하므로 애초에 안 붙는다
- 게임 경로는 앞단 워커가 이 헤더를 **지운다**

## 걸린 것 — `_redirects` 규칙이 먹지 않았다

앱 안쪽 주소(`/m-hairsalon/home`, `/m-hairsalon/room/ABCD`)가 404 였다.

같은 폴더의 `_headers` 는 잘 듣고(매니페스트 `max-age=3600`, `sw.js` `no-cache` 확인),
`ads.txt` 도 올라갔는데 **`/m-hairsalon/*` 규칙만 무시됐다.** 저장소에는 LF 로 들어가 있어
줄바꿈 문제도 아니었다.

이유를 캐는 대신 **우리가 통제하는 자리로 옮겼다.** 실제 주소를 내주는 것은 어차피 앞단
워커다. 404 가 오고 확장자가 없는 요청이면 앱의 첫 문서를 200 으로 돌려준다.

여기서 한 번 더 걸렸다. 첫 시도는 `/m-hairsalon/index.html` 을 불렀는데 **Pages 가 그것을
`/m-hairsalon/` 으로 되돌린다(308).** 리다이렉트를 따라가지 않는 설정이라 그 308 을 받아
들고 "실패" 로 판단해 버렸다. 폴더 주소를 부르게 고쳐 해결했다.

확장자가 있는 요청은 그대로 404 로 둔다 — 없는 자산을 첫 문서로 감추면 빠진 파일을 영영
못 알아챈다.

# 재검토 요청 접수 (2026-09-05)

넣기 직전에 **두 가지를 더 잡았다.** 사용자가 "지금 재검토 요청하면 안 되냐" 고 물어봐 준
덕에 확인하다 나왔다. 그대로 넣었으면 또 반려됐을 것이다.

### ① 사이트가 스스로 "진짜는 저쪽" 이라고 말하고 있었다

포트폴리오의 모든 페이지가 `canonical` 과 `og:url` 로 **옛 워커 주소**
(`wonderful.shworld.workers.dev`)를 가리켰다. `content/profile.json` 의 `siteUrl` 이 작업
트리에서 옛 값으로 되돌려져 있었고, 그 상태로 빌드된 `dist/` 가 배포돼 있었다.

애드센스가 심사하는 주소는 `shworld.cloud` 인데 **그 사이트가 스스로를 사본이라고 말하는**
상태였다.

### ② 게임 문서들이 첫 화면의 사본으로 취급되고 있었다

미리 그린 페이지들은 같은 껍데기(`index.html`)를 쓰므로 `canonical` 이 전부 앱의 첫 주소를
가리켰다. 그러면 검색엔진은 `/guide` 와 `/privacy` 를 첫 화면의 사본으로 보고 **그 글을 따로
세지 않는다.** 오늘 백지를 고쳐 얻은 2,970자와 4,465자가 통째로 날아갈 뻔했다.

`tools/apply-prerender.mjs` 가 경로마다 자기 주소를 심게 고쳤다.

### ③ 사이트맵에 게임이 없었다

게임은 별도 저장소라 포트폴리오의 사이트맵 생성기가 알지 못했다. 저장소가 다르다고 크롤러가
알아서 찾아가지는 않는다. 생성기에 넣어 11개 주소를 모두 알린다.

`public/sitemap.xml` 을 직접 고쳤다가 다음 빌드에 지워진 것을 보고 알았다 —
`scripts/build-content.mjs` 가 생성하는 파일이다.
